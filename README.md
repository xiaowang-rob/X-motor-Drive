# X-motor-Drive

## xfoc 库化计划

### 目标与当前状态

目标是让不同板卡复用同一套电机控制代码：优先将 `firmware/xfoc` 整理为**平台可注入的源码库**，之后再按需要拆分组件或发布预编译 `.a`。

当前 `firmware/xfoc/CMakeLists.txt` 已通过 `add_library(xfoc STATIC ...)` 构建静态库，板级工程通过 `add_subdirectory(...)` 和 `target_link_libraries(...)` 使用它，无需重新实现静态库构建机制。

目前库内同时包含控制算法、设备抽象、参数与保护等服务、协议处理和应用启动，更接近电机控制固件框架，而非纯算法库。库化的重点是明确平台边界、公开接口和依赖契约，而不是仅生成一个 `.a` 文件。

以下内容为待实施计划，不代表已经完成。

### 当前需要解决的问题

- **板级耦合**：`ctl/core.c` 直接使用 `g_sense`、`g_gate`，`ctl/obs.c` 使用 `g_enc` 并调用 `bsp_enc_init()`；`cmd_process.c` 还直接依赖板级复位、时间与通信接口。换板时需要提供同名全局变量和 BSP 函数。
- **公开头依赖泄露**：`ctl/control.h`、`ctl/tune_alg.h`、`utils/filter.h` 通过 `bsp_math.h` 依赖 CMSIS-DSP；`filter.h` 的公开结构还直接包含 CMSIS-DSP 类型。目前仅向库内部注入 include 路径，不能完整表达消费者需要的公开依赖。
- **启动与宿主调度混合**：`xfoc_main.c` 的 `xfoc_start()` 在初始化后进入无限循环，不能作为正常返回的库初始化接口。
- **数学库依赖未由 target 完整表达**：DSP、标准数学库和 `xfoc` 分散加入最终程序的链接列表，存在静态库链接顺序问题。

### 第一阶段：整理为可复用源码库

#### 1. 明确 CMake 依赖

- [ ] 将 CMSIS-DSP 建模为独立的 imported target，配置对应平台的库文件、DSP/CMSIS include 路径及必要的编译定义。
- [ ] 让 `xfoc` 显式依赖数学库，而不是要求最终应用手工排列链接顺序。
- [ ] 当前公开头暴露 CMSIS-DSP 类型，因此数学依赖应使用 `PUBLIC`；未来消除公开类型依赖后，再评估改为 `PRIVATE`。
- [ ] 将实现侧 BSP/HAL 的编译需求通过平台接口 target 注入，不把板级实现绑定进算法库，也避免 target 循环依赖。
- [ ] 移除 CubeMX 链接列表中提前加入的重复数学库配置，统一依赖管理；注意 CubeMX 重新生成可能覆盖生成文件中的修改。

预期依赖关系：

```text
板级可执行文件
    └── xfoc
         └── CMSISDSP
              └── m
```

最终链接顺序应满足“引用者在前，提供符号的库在后”：

```text
消费者对象 → xfoc → CMSIS-DSP → m
```

`target_link_libraries` 负责传递链接依赖，不会将依赖库自动合并进 `libxfoc.a`。

#### 2. 明确公开 API

- [ ] 区分对外头文件与内部实现头文件，不再默认将全部内部头目录作为公开 API。
- [ ] 逐步形成稳定的 `include/xfoc/` 公开头目录。
- [ ] 将数学适配契约从板级 `bsp_math.h` 中分离；按需要隐藏滤波器实现结构，减少公开 API 对 CMSIS-DSP 的绑定。

建议逐步演进的目录布局：

```text
firmware/xfoc/
├── include/xfoc/   # 对外 API
├── ctl/            # 内部控制实现
├── abs/            # 设备抽象
├── srv/            # 服务
└── CMakeLists.txt
```

#### 3. 注入平台设备与回调

- [ ] 沿用现有 `abs` 层的 `ops + void *dev` 设计，通过初始化配置或上下文传入编码器、采样、PWM 等设备。
- [ ] 通过明确的平台契约提供时间、设备初始化等必要回调，逐步替代库内对 `bsp_cfg.h` 和板级 `g_*` 的直接访问。
- [ ] 板级仍可保留自己的设备全局变量，但由板级装配并传给库，而不是由库自行获取。
- [ ] 区分板级设备全局与库自身的运行状态，不将所有全局变量一概当作板级依赖处理。

#### 4. 分离初始化与宿主调度

- [ ] 让库初始化完成后返回，并报告初始化结果。
- [ ] 将无限循环留在板级 `main()` 或 RTOS 任务中。
- [ ] 定义清晰的周期执行入口，由宿主负责主循环、任务和中断调度。

本阶段完成后，换板应主要涉及平台适配与设备装配，不需要修改控制算法内部实现。

### 第二阶段：按需要拆分组件

先明确内部边界，再决定是否拆为多个 target，不要求第一阶段一次性重构全部服务。

- [ ] `xfoc_core`：控制算法与必要的设备抽象。
- [ ] `xfoc_services`：参数、保护、调度等服务。
- [ ] `xfoc_protocol`：通信与命令处理。
- [ ] 板级应用：启动、设备装配、复位及烧录相关行为。

协议处理、IAP、状态灯等应用功能可逐步移入可选组件或宿主，避免成为算法核心的强制依赖。

### 第三阶段：按需要发布预编译库

源码库是当前优先交付方式，可随宿主工具链和平台配置重新编译。发布预编译 `.a` 时，还需要：

- [ ] 配套版本的稳定公开头文件。
- [ ] 平台适配接口、外部符号契约及接入示例。
- [ ] CMSIS-DSP 等依赖及可供消费者使用的 CMake 包配置。
- [ ] 明确 CPU、FPU、浮点 ABI、结构布局与影响 ABI 的配置约束。

当前 `xdr_s` 的工具链配置为 `cortex-m4 / fpv4-sp-d16 / hard-float`，对应产物不能作为任意 MCU 通用的二进制库。startup、HAL/BSP 实现、链接脚本与调度仍由宿主提供。

### 验证与验收

- [ ] 使用独立消费者 target 验证公开头文件及依赖传播，不依赖应用私下补充 include 路径。
- [ ] 运行板级编译，确认 `xfoc`、CMSIS-DSP 和 `m` 的链接依赖可正常解析。
- [ ] 将重复中断定义等板级构建问题与库化问题分别处理，不通过屏蔽错误验证库化结果。
- [ ] 验证初始化能够返回，周期入口可由宿主调用。
- [ ] 后续以另一板卡或最小平台适配验证迁移边界；算法测试与硬件运行验证分别进行。

当前板级编译命令：

```bash
python3 firmware/tools/build.py build --board=xdr_s --type=app
```
